# Terraform vs Terragrunt: same AWS infrastructure, two approaches

This repository provisions the same illustrative AWS stack with plain Terraform and Terragrunt:

- VPC with public and private subnets
- EKS cluster with a managed node group
- PostgreSQL RDS instance
- Development and production environment examples

The reusable Terraform modules under `modules/` are shared by both approaches.

## Repository layout

```text
modules/                 Shared Terraform modules: vpc, eks, rds
terraform/
  bootstrap/             Creates an S3 remote-state bucket
  environments/
    dev/                 One Terraform root module and state for dev
    prod/                One Terraform root module and state for prod
terragrunt/
  root.hcl               Shared backend/provider configuration
  live/
    dev/                 env.hcl plus separate vpc/eks/rds units
    prod/                env.hcl plus separate vpc/eks/rds units
ARTICLE.md               Article explaining the comparison
```

## Important before applying

1. Replace the example AWS account IDs (`111111111111` and `222222222222`) with your actual account IDs.
2. Replace the example state bucket names with globally unique names. The bootstrap bucket name must match the name configured by the corresponding environment/backend.
3. Replace `203.0.113.10/32` in both environment configurations with the trusted public IP/CIDR ranges for your administrator workstation or CI runner. This is a documentation-only IP range and will not give you access to the EKS API.
4. Confirm the selected EKS Kubernetes version is currently supported in your AWS region and update `cluster_version` as needed.
5. Review the module/provider versions and commit `.terraform.lock.hcl` files generated by `terraform init` for each Terraform root module.
6. This creates billable resources, including EKS, NAT Gateways, and RDS. Review the plan and expected costs before applying. Production deletion protection is enabled.
7. This repository is an example, not a production-ready reference architecture. Review IAM, network access, backups, monitoring, encryption/key-management requirements, and operational access for your organization.

## Tool versions

The `.tool-versions` file records the versions used when this example was assembled. Use a compatible pinned Terraform and Terragrunt version and review release notes before upgrading.

## Bootstrap the remote-state bucket

Run this once in each AWS account that needs its own state bucket. The bootstrap uses local state; store that state securely and retain it because it manages the bucket used by the other configurations.

```bash
cd terraform/bootstrap
terraform init
terraform apply -var="bucket_name=mycompany-tfstate-111111111111"
```

Repeat for the production account with its bucket name. The bootstrap enables versioning, server-side encryption, public-access blocking, and a bucket policy that denies non-TLS requests. The bucket name in the backend configuration must match exactly.

## Approach 1: plain Terraform

Authenticate to the development AWS account, then:

```bash
cd terraform/environments/dev
terraform init
terraform fmt -recursive
terraform validate
terraform plan
terraform apply
```

`terraform.tfvars` is loaded automatically. VPC, EKS, and RDS are in one root module and one state file per environment. Terraform's own dependency graph orders the module operations based on their input/output references.

For production, authenticate to the production account and run the equivalent commands under `terraform/environments/prod`.

## Approach 2: Terragrunt

Authenticate to the development AWS account, then:

```bash
cd terragrunt/live/dev
terragrunt run --all validate
terragrunt run --all plan
terragrunt run --all apply
```

Each component (VPC, EKS, RDS) has its own state file. The shared `root.hcl` generates backend and provider configuration, while `dependency` blocks pass outputs between units and provide the graph used by `run --all`.

Running `terragrunt apply` directly inside `eks/` does not deploy VPC first. The VPC unit must already exist. Use `run --all` when you want Terragrunt to orchestrate all units in dependency order.

For production, authenticate to the production AWS account and run the equivalent commands under `terragrunt/live/prod`.

## State layout

Plain Terraform:

```text
one state per environment
  dev/terraform.tfstate
  prod/terraform.tfstate
```

Terragrunt:

```text
one state per component
  dev/vpc/terraform.tfstate
  dev/eks/terraform.tfstate
  dev/rds/terraform.tfstate
  prod/vpc/terraform.tfstate
  prod/eks/terraform.tfstate
  prod/rds/terraform.tfstate
```

The actual S3 object key includes the project and path relative to `terragrunt/root.hcl`.

## Validation status

The repository has not been applied against a live AWS account in this package. Run formatting, initialization, validation, and plans in a sandbox account before deployment. A successful `validate` does not prove that AWS permissions, quotas, service availability, or every runtime behavior are correct.
